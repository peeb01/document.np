GPU Computing & AccelerationCore

Grid, Blocks & Threads Model

Unlike CPU multithreading where each thread runs independent complex logic, GPUs execute millions of lightweight threads concurrently using the SIMT (Single Instruction, Multiple Threads) architecture. Threads are organized into Blocks, and Blocks are arranged into a Grid.

The 3-Tier Hierarchy: Grid, Block, and Thread

Every GPU launch decomposes into three conceptual layers:

  • 1. Thread (Individual Worker): The smallest execution unit. Each thread has its own register state and thread ID.
  • 2. Block (Worker Team / Cooperative Group): A group of threads (typically 128, 256, or 512). All threads in a block run on the same Streaming Multiprocessor (SM) and can synchronize via gpu.sync_threads().
  • 3. Grid (The Entire Workforce): The collection of all thread blocks dispatched for a kernel launch across the entire GPU chip.

The Neighborhood Analogy

If you are new to GPU thread hierarchies, think of the GPU as a master-planned housing community:

  • block_dim_x() = House Capacity: Number of workers assigned to each house (e.g. 256 workers per house).
  • block_idx_x() = House Number: Street address of the house (House #0, House #1, House #2...).
  • thread_idx_x() = Person ID within House: Which person you are inside your house (Person 0 to 255).
  • Global Index = Unique Citizen ID: A globally unique ID across the entire town used to index into the memory array.

Why Not a Flat 1D List of 1,000,000 Threads?

Physical GPU silicon is built out of multiple independent Streaming Multiprocessors (SMs). The hardware schedules one Block per SM. Grouping into blocks allows the GPU hardware to scale across small laptops (few SMs) to massive server GPUs (dozens of SMs) without changing your code!

The Global Index Formula: thread_idx_x() + block_idx_x() * block_dim_x()

To find which array element a thread is responsible for, combine the block coordinate and thread coordinate into a single 1D global index:

  • Person 5 in House 0: 5 + (0 * 256) = Index 5 (processes array element a[5]).
  • Person 0 in House 1: 0 + (1 * 256) = Index 256 (processes array element a[256]).
  • Person 10 in House 2: 10 + (2 * 256) = 10 + 512 = Index 522 (processes array element a[522]).
  • Person 255 in House 3: 255 + (3 * 256) = 255 + 768 = Index 1023 (processes array element a[1023]).
global_index.np
1# Standard 1D Global Thread Index Calculation
2idx := gpu.thread_idx_x() + gpu.block_idx_x() * gpu.block_dim_x()

Boundary Checks: Why 'if idx < n:' is Mandatory

Because thread blocks must be uniform multiples (e.g. 256 threads per block), the total number of threads launched often exceeds the exact size of your data:

  • Suppose your array has N = 1,000 elements.
  • If block size = 256, you must launch 4 blocks (4 * 256 = 1,024 threads).
  • Threads 0 through 999 process valid array elements.
  • Threads 1,000 through 1,023 have no valid data to process! Without a guard, they would read/write out-of-bounds memory and crash your program.
  • Always wrap your kernel computation in an 'if idx < n:' boundary check!
boundary_guard.np
1kernel func safe_vector_add(a, b, c, n: int):
2 idx := gpu.thread_idx_x() + gpu.block_idx_x() * gpu.block_dim_x()
3
4 # Critical Boundary Guard: Prevents out-of-bounds memory access!
5 if idx < n:
6 c[idx] = a[idx] + b[idx]

Always Guard Kernel Logic

Omitting 'if idx < n:' will cause memory corruption, segmentation faults, or silent calculation errors when data length is not an exact multiple of the block size.

Calculating Optimal Grid & Block Sizes in NP Code

Use this standard mathematical formula to determine launch parameters for any array length N:

2
3# Recommended block size: 128, 256, or 512 (256 is the standard default)
4int block_size = 256
5
6# Ceiling division: ensures enough blocks cover all elements
7int grid_size = total_elements / block_size
8if (total_elements % block_size) > 0:
9 grid_size = grid_size + 1

11print("Total elements:", total_elements)
